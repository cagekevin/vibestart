# 施工图（plan）

**动代码之前先写这里。** 一份 plan 只服务**一次**改动。

## 顺序是固定的

**原语 → 契约 → 形状 → 数据流 → 同类实现 → 步骤。**

前四步是策划，后两步是施工。跳过前四步直接写「改哪几个文件」，等于在赌：赌你不会多开一个入口、赌数据结构撑得住、赌没人已经在做同一件事。

- **原语**：这次动到哪几个不可再分的构件？有没有新增？新增一个原语必须写清「它为什么不可再分、谁组合它、唯一入口是什么」——写不出就是还没想清。
- **契约**：对外承诺变成什么样（端点 / 命令 / 导出签名 / 文件路径）。成功返回什么、失败返回什么、**不许**返回什么。
- **形状**：支撑这份契约的数据长什么样。字段、必填与可空、状态枚举；新增一个状态要同时改哪几处。
- **数据流**：谁产生 → 怎么变形 → 谁消费。每步谁写谁读、失败停在哪。
- **同类实现**：仓库里有没有已经在做同一件事的？有 ⇒ 复用或改它，写清改哪个、删哪个；没有 ⇒ 说明为什么必须新建。

## 写完就冻结

**不长期维护。** 落地后它的价值结束：删掉，或把结论并进 `spec/` / `architecture.md`，过程留在 `daily/架构日志/`。留着继续改，它就是第二份 spec。

**「为什么这样切」不留在 plan 里，写进代码。** 被切开的那几个文件，各自在头注释里写清「为什么存在 / 不做什么 / 边界在哪」（见 `docs/architecture.md` 的「模块头」）。ADR 只收判据，切分理由归代码 —— 这样它跟着代码一起被改，不会在文档里变成第二份真相。

|        | spec                       | plan                       |
| ------ | -------------------------- | -------------------------- |
| 回答   | 这个能力**对外**是什么行为 | 这**一次**怎么把它改成那样 |
| 寿命   | 长期，随行为演进           | 一次，落地即作废           |
| 冲突时 | **spec 赢**                | plan 只是执行细节          |

plan 里不重复 spec 的行为表，引用它即可（`docs/spec/<能力>.md`）。

## 文件名

`<YYYY-MM-DD>-<能力>.md`。日期在前，目录天然按时间排；同名能力再改一次就多一份新的。

## 什么时候可以不写

改一个笔误、调一行文案、纯重命名。**只要改行为、改结构、动外部契约，就必须先有 plan。**

## 格式（照抄这份骨架）

```md
# <YYYY-MM-DD> · <能力> · 施工图

- **状态**：草稿 / 已确认 / 已落地
- **对应 spec**：`docs/spec/<能力>.md`（没有就先补）
- **会碰到哪几条 ADR**：`<编号>`；写之前先读那几条的「违反时的判据」

## 1. 原语

动到哪几个原语；新增的写清为什么不可再分、谁组合它、唯一入口在哪。对照 `docs/architecture.md` 的「原语」。

## 2. 契约

对外承诺：端点 / 命令 / 导出签名 / 文件路径。成功、失败、不许返回什么。变了谁受影响。

## 3. 形状

类型、字段、必填与可空、状态枚举；新增状态要同时改哪几处。

## 4. 数据流

谁产生 → 怎么变形 → 谁消费。每步谁写谁读、失败停在哪。

## 5. 同类实现

仓库里已有的同类东西在哪。复用 / 改它 / 新建，以及为什么。

## 6. 步骤

| #   | 改哪里 | 做什么 | 怎么验证 | 回退 |
| --- | ------ | ------ | -------- | ---- |

每一步都要能独立验证；不能验证的，拆到能为止。

## 7. 验收

命令 + 期望输出；对应 spec 的哪几条行为。

## 8. 落地后

删掉本文件，或把结论并进 `spec/` / `architecture.md`；过程写进 `daily/架构日志/<NN>-<区域>-<主题>-<日期>.md`。
```
