# 开局：先把约定定下来

> **只在这个文件还没被删掉时读它。** 它只在项目刚建好、还没写业务代码时有用 —— 下面的事做完就删掉，并从 `docs/README.md` 的映射表里删掉它那一行。

写第一行业务代码之前，先答完下面几件事。答案写进各自该在的文件，**不要写在这份引导里**，它会被删。

## 0. 技术栈现在定，要换现在换 → `docs/context.md`

这个项目由 vibestart 按选定栈生成，生成器**不提供中途换栈**。想换后端语言、框架或 UI 方案，只能趁现在：项目里还没有业务代码，这是整个项目最便宜的换栈时刻。

换栈大致三个层次，代价从低到高，想清楚你要动的是哪层：

- **换后端语言**（如 Rust）：Web 前端可以原样保留，只重写 `apps/server` 和部署
- **换桌面壳**（如 Electron → Tauri）：UI 和后端都不动，重写 `apps/desktop`
- **换 UI 体系**（如 Web 组件方案 → 原生 UI 框架）：动静最大，`packages/ui` 和全部界面重写，本项目的样式、主题与文档约定全部作废

确定不换 ⇒ 以后就不再换，把「为什么是这个栈、排除了哪些替代方案」写进 `docs/context.md`，照常往下走。

**判据**：换栈的理由写在 `docs/context.md` 里，且能挡住未来「顺手换个更时髦的框架」的提议。

## 1. 这是什么 → `docs/context.md`

- 给谁用：一个人、一个团队、还是一类陌生人？
- 解决什么问题：不用这个项目，用户现在怎么办？
- **不做什么**：三件最容易被顺手加进来的事，明确排除。
- 三个术语：只有这个项目才这么叫的词，各一句话。

**判据**：别人读完能判断「这个需求该不该做」。判断不了，就是没写清。

**`README.md` 也要改**：它现在开头只有技术栈，读的人不知道这个项目是做什么的。补一句话（它是什么、给谁），或直接在开头指向 `docs/context.md`。

## 2. 它对外怎么表现 → `docs/spec/<能力>.md`

先只写**核心的一到三个能力**，每个写清：输入、输出、失败。

**判据**：能照它写出测试。写不出测试，说明还没定义清楚。

## 3. 它长什么样 → `docs/architecture.md`

- **原语**：哪几个构件不可再分？拆开之后每一半还能单独成立吗？
- **分层**：目录 → 一个职责，写清「只放什么、不许放什么」。
- **依赖方向**：谁不许 import 谁（只写会被违反的那几条）。
- **不变量**：跨模块的硬约束，一到三条。

**判据**：新人能据此判断「这个文件该放哪」。

## 4. 它会被改在哪 → `scripts/arch-index.mjs` 的 `AREAS`

默认的七个区域按技术层切，换成这个项目的职责名。**区域名要和「分层」用同一套词。**

**判据**：任何一个改动都能归到一个区域，且只归一个。

## 5. 这个项目特有的判据 → `docs/adr/`

基础 9 条已经覆盖通用的坑。只有「基础 9 条没覆盖 + 会反复发生 + 类型拦不住」时才写新 ADR。

**开局零 ADR 是正常的。** 不要为了显得规范而写。
