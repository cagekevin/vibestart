# 架构（现状）

> 只写**代码里读不出来的**东西：分层、依赖方向、跨模块不变量、数据从哪到哪。
>
> 与代码**同一批提交**更新。两者不一致时以代码为准，然后回来改这里 —— 这份文件是代码的摘要，不是它的上司。
>
> 单模块内部的结构不写：读那个文件比读这里快。

## 原语

不可再分的构件，其余一切由它们组合。数量不设上限 —— 判据是「拆开之后，每一半还能单独成立吗」，能，就说明它还不是原语。每个写：**是什么、唯一入口在哪、禁止什么。**

每次写 plan 都从这里开始：这次动到哪几个原语、要不要新增一个。新增必须能回答「它为什么不可再分、谁组合它、唯一入口是什么」，答不出就是分层没想清。

## 根目录

根只放**长期存在**的东西，其余一律有归属。

| 放什么   | 例                                                                                                       |
| -------- | -------------------------------------------------------------------------------------------------------- |
| 配置与锁 | `package.json`、`pnpm-workspace.yaml`、`vite.config.ts`、`tsconfig.json`、`knip.json`、`vibestart.jsonc` |
| 入口文档 | `README.md`、`AGENTS.md`                                                                                 |
| 目录     | `apps/`、`packages/`、`scripts/`、`docs/`、`daily/`                                                      |
| 部署     | `Dockerfile`、`docker-compose.yml`、`.dockerignore`                                                      |

**不放**：临时文件、构建产物、本地数据、一次性脚本、随手写的 `test-*.ts`。

| 东西                 | 去哪                                            | 已被忽略 |
| -------------------- | ----------------------------------------------- | -------- |
| 临时文件、导出、抓包 | `.tmp/`                                         | 是       |
| 构建产物             | `dist/`、`coverage/`、`.vite/`、`*.tsbuildinfo` | 是       |
| 本地数据库           | `*.db`、`*.sqlite`、`*.sqlite3`                 | 是       |
| 日志、备份           | `*.log`、`*.bak`                                | 是       |
| 一次性的验证脚本     | `scripts/`，用完删                              | 否       |

`.tmp/` 里的东西随时可以删：要留下的是结论，不是文件。

**判断标准**：这个文件三个月后还在吗？在 ⇒ 根或对应目录；不在 ⇒ `.tmp/`，并且不许进 git。

### 目录命名

目录名必须是**一个职责**，不是垃圾桶。判据：能一句话说出「这里面只放什么」，说不出来就该拆。

- **禁**：`utils/`、`common/`、`helpers/`、`misc/`、`shared/` —— 这些名字等于「还没想清」。
- **`src/clients/` 是外部客户端的唯一构造点**：一个外部系统一个文件（`api.ts`、`auth.ts`、`query-client.ts`）。用户看得见的失败呈现放 `src/feedback/`。出现第三类东西（格式化、业务规则、组件）就另开目录，不许往里塞。
- **判据是职责数，不是行数**：一个文件只承担一个职责 —— 出现第二个「为什么要改它」的理由，就是两个职责，该拆。200 行的纯计算可以只有一个职责；80 行里塞了校验、格式化、发请求就是三个。目录同理：里面有几个职责，就是几件事。
- **按职责命名，不按技术层命名**：`billing/`、`viewport/`、`export/` 是好名字；`services/`、`models/`、`types/` 不是。

### 模块头

每个模块（一个文件，或一个目录的入口）开头三行，缺一行就说明没想清：

1. **为什么存在**：它解决什么，没有它会被什么替代。
2. **不做什么**：最容易被人塞进来的那件事，明确拒绝。
3. **边界**：谁能调它、它调谁、出问题从哪查。

理由写在代码里，不写进 ADR —— ADR 只收判据（三条都成立才写），切分理由留在模块头，跟着代码一起改。
