# 行为规格（spec）

一份 spec = 一个能力**对外**怎么表现。读者是接下来要改这个能力的人与 AI。

写**可观察行为**：输入、输出、失败、边界。不写函数名、文件路径、表结构 —— 那些属于 `architecture.md` 与代码。

## 什么时候写

- **写**：这个能力有分支、有失败路径、有对外契约（HTTP / CLI / 文件格式 / 计费 / 权限），或者「这样做对不对」需要争论。
- **不写**：一条直路、没有分支、测试名就能说清。别为了凑格式造 spec —— 一份没人读的 spec 比没有更糟。

## 状态

`草案`（还在改）→ `生效`（代码按它实现）→ `已退役`（能力没了，文件留着说明为什么没的）。

状态写在文件头，**改状态不改正文**。行为变了就改正文并留版本痕迹（git 负责历史，别在正文里写「原来是这样」）。

## 文件名

`<能力>.md`，用能力的名字，不用编号：编号会随拆分合并失效，名字不会。

## 格式（照抄这份骨架）

````md
# <能力>

- **状态**：草案
- **拥有者**：<谁说了算>
- **关联**：ADR-0005、TD-03-1

## 做什么

一段话：用户视角下这个能力是什么。

## 行为

| # | 输入 | 期望 | 失败时 | 验收 |
| --- | --- | --- | --- | --- |
| 1 | | | | 哪条测试 / 哪条命令 |

「验收」一格必须能被一条测试或一条命令证明。写不出来，说明这条还没想清。

## 不做

明确排除的相邻行为。不写就会被顺手加上。

## 不变量

跨模块必须一直成立的事，例如「提交永不因并发失败」。

## 未决

还没定的问题 + 谁来定。
````
